# 炮塔建造系统对照评审（Google Doc vs 当前实现）

## 1. 评审范围
- 外部文档：`https://docs.google.com/document/d/1dZ6oUFiq7KBLhBpsKUZl3oq8uf_bus9LZGERKfRLNHU/edit?tab=t.0`
- 本地代码基线（2026-02-19）：
  - `res://game/player/player.gd`
  - `res://game/player/ground_block_grid_overlay.gd`
  - `res://game/world/infinite_ground/infinite_ground.gd`
  - `res://game/features/items/temp_turret/temp_turret.gd`

## 2. 一句话结论
这份外部文档的“大规模 3D 体素/SDF 引擎”方案，不适合当前项目直接照搬；但其中“逻辑层与表现层解耦、约束驱动放置、结构完整性规则”三点，**非常值得借鉴**，并且可以在现有 2D 架构中低风险落地。

## 3. 当前实现现状（简述）
- 当前放置链路是清晰可用的：
  - 点击物品栏 -> 激活格子预览 -> 鼠标左键放置（`player.gd`）。
- 当前系统已有基础约束：
  - 不能与玩家重叠、不能与载具碰撞箱重叠、同格去重。
- 当前地面系统是“离散格子 + 物理查询”：
  - `infinite_ground.gd` 已有块级生成、支撑判断、掉落块逻辑。

结论：项目已经有一个可迭代的 `grid placement` 垂直切片，不需要引入重型底层重构。

## 4. 值得借鉴的点（按优先级）

### P0（建议立刻做）
1. 逻辑-表现解耦（Logic vs Visual）
- 外部文档强调：数据层和渲染层分离。
- 本项目可落地版本：
  - 新增“炮塔放置数据”结构（位置、朝向、等级、状态），由管理器维护；
  - `temp_turret.gd` 只负责渲染与交互，不直接承担权威数据。
- 收益：后续加“升级/拆除/存档/网络同步”不会反复改视觉节点。

2. 放置规则显式化（Constraint Set）
- 当前规则分散在 `player.gd` 多个函数中。
- 建议抽成统一 `can_place_turret(cell)` 判定入口：
  - 玩家占用检测
  - 载具碰撞检测
  - 重复格检测
  - 边界检测
- 收益：可测试、可扩展、减少回归。

### P1（中期建议）
1. 结构完整性轻量版（Structural Integrity Lite）
- 外部文档讲的是 Valheim 风格图传播。
- 本项目可先做简化版：
  - 炮塔必须“有地基支持”（脚下有地块或载具顶面白名单）；
  - 支撑失效时进入“失效/掉落/禁用”状态。
- 收益：玩法更合理，避免“悬空炮塔”。

2. 双模式建造交互（Dual Mode）
- 外部文档建议自由模式 + 模块模式。
- 本项目可简化为：
  - `Snap Mode`（当前格子吸附）
  - `Free Preview Mode`（仅预览，落点仍受规则约束）
- 收益：手感提升，不破坏现有架构。

### P2（长期探索，不建议近期投入）
1. SVO / Dual Contouring / MDC / Transvoxel
- 这些是面向大规模 3D 体素地形引擎的核心技术。
- 当前项目是 2D 平台动作 + 格子地面，直接迁移成本高、收益低。
- 建议仅保留为“未来技术储备”，不进入近期里程碑。

## 5. 不建议照搬的内容
- 直接上 SDF 全管线、GPU 程序化网格、WFC 全局生成、动态 NavMesh 重建。
- 原因：与当前项目目标/体量不匹配，会明显增加复杂度与维护成本。

## 6. 推荐落地顺序（最小风险）
1. 抽离炮塔放置规则为单一判定入口（P0）。
2. 新增“炮塔逻辑数据层”与“场景表现层”分离（P0）。
3. 加入轻量结构完整性（P1）。
4. 视玩法反馈再做双模式交互（P1）。

## 7. 对当前需求的直接指导
- 如果近期目标是“可玩性稳定提升”，优先做 `P0 + P1`。
- 如果目标是“重做世界底层技术”，才考虑文档中的 `P2` 路线。
